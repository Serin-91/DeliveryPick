# DeliveryPick 비회원 공개 조회 전환 구현 지시서

## 1. 목표

DeliveryPick의 첫 화면(`/`)을 공개 맛집 목록으로 사용한다.

- 비회원: 목록, 검색, 필터, 정렬, 상세 조회 가능
- 회원: 기존 기능 유지
- 맛집 등록과 `오늘 뭐 먹지?`: 로그인 필요
- 수정·삭제: 작성자 본인만 가능
- 기존 지역, 다중 메뉴, 대표 메뉴, 정렬, 오늘 뭐 먹지 기능은 그대로 유지

핵심 원칙은 **읽기는 공개, 쓰기는 로그인, 수정·삭제는 작성자만**이다.

## 2. 화면별 권한

| 화면/기능 | 비회원 | 로그인 회원 | 작성자 본인 |
|---|---:|---:|---:|
| `/` 목록·검색·필터·정렬 | 가능 | 가능 | 가능 |
| `/delivery/[id]` 상세 | 가능 | 가능 | 가능 |
| `오늘 뭐 먹지?` 실행 | 불가 | 가능 | 가능 |
| `/register` 등록 | 불가 | 가능 | 가능 |
| `/delivery/[id]/edit` 수정 | 불가 | 불가 | 가능 |
| 삭제 | 불가 | 불가 | 가능 |

## 3. 공개 페이지 인증 처리

### 목록 `/`

- `useRequireAuth()`를 제거한다.
- 로그인하지 않아도 `deliveries`와 연결된 `delivery_menus`를 즉시 조회한다.
- 인증 상태 확인과 데이터 조회를 분리한다. 데이터 조회가 `user` 존재 여부에 의존하면 안 된다.
- 현재 목록, 지역, 검색, 카테고리, 앱, 정렬 로직은 유지한다.
- 작성자 이메일은 절대 공개하지 않는다. 저장된 `user_nickname`이 없으면 `익명`으로 표시한다.

### 상세 `/delivery/[id]`

- `useRequireAuth()`를 제거하고 비회원도 조회할 수 있게 한다.
- 수정·삭제 영역은 다음 조건에서만 렌더링한다.

```ts
const isOwner = Boolean(user && item && user.id === item.user_id)
```

- 비회원과 다른 회원에게는 수정·삭제 버튼을 아예 보여주지 않는다.
- 삭제 함수 내부에서도 소유권을 다시 확인하고, 삭제 쿼리에 작성자 조건을 추가한다.

```ts
.delete()
.eq('id', item.id)
.eq('user_id', user.id)
```

- 데이터 없음과 조회 오류를 구분해 사용자에게 표시한다.

### 선택 인증 훅

- 공개 화면용으로 리다이렉트하지 않는 `useAuth()` 훅을 만들거나 동등한 방식으로 처리한다.
- 반환값은 최소 `{ user: User | null, loading: boolean }`이어야 한다.
- `getSession()` 초기 확인 후 세션이 없어도 반드시 `loading=false`가 되어야 한다.
- `onAuthStateChange`를 구독하고 언마운트 시 해제한다.
- `/register`, `/delivery/[id]/edit`은 계속 강제 인증을 사용한다.

## 4. 헤더 요구사항

`Header`의 `user` 타입을 `User | null`로 변경한다.

### 비회원 헤더

- `오늘 뭐 먹지?`
- `맛집 등록`
- `로그인`
- `회원가입`

`오늘 뭐 먹지?`와 `맛집 등록`은 비회원에게도 보여주되 클릭하면 실제 기능을 실행하지 않고 로그인 안내 모달을 연다.

모달 문구는 `회원가입이 필요한 서비스입니다`가 아니라 **`로그인이 필요한 서비스입니다`**로 쓴다. 기존 회원도 있기 때문이다.

#### 오늘 뭐 먹지 모달

> 로그인이 필요한 서비스입니다.  
> 로그인하면 오늘의 배달 메뉴를 추천받을 수 있어요.

버튼: `로그인`, `회원가입`, `취소`

#### 맛집 등록 모달

> 맛집을 등록하려면 로그인이 필요합니다.

버튼: `로그인`, `회원가입`, `취소`

- 브라우저 `alert()` 대신 재사용 가능한 모달 컴포넌트를 사용한다.
- 모달은 바깥 영역 클릭과 `Esc`로 닫히고, `role="dialog"`, `aria-modal="true"`, 접근 가능한 제목을 제공한다.
- 모바일에서 네 개 버튼 때문에 헤더가 깨지지 않도록 작은 화면에서는 텍스트 축약, 아이콘, 메뉴 또는 줄바꿈 중 현재 디자인에 맞는 방식을 사용한다.

### 회원 헤더

현재 동작을 유지한다.

- 닉네임
- `오늘 뭐 먹지?`
- `맛집 등록`
- 로그아웃

로그아웃 후에는 공개 목록을 계속 볼 수 있도록 `/login`이 아닌 `/`로 이동하고 화면을 갱신한다.

## 5. 로그인 후 원래 기능으로 복귀

로그인·회원가입 페이지는 안전한 내부 경로용 `next` 값을 지원해야 한다.

예시:

```text
맛집 등록 클릭 → /login?next=/register
오늘 뭐 먹지 클릭 → /login?next=/?pick=1
수정 URL 직접 접근 → /login?next=/delivery/{id}/edit
```

- 로그인 성공 후 `next`가 있으면 해당 경로로, 없으면 `/`로 이동한다.
- 회원가입 성공 후에도 같은 규칙을 적용한다.
- 로그인 화면의 `회원가입` 링크와 회원가입 화면의 `로그인` 링크가 `next` 값을 보존해야 한다.
- 이미 로그인한 사용자가 로그인/회원가입 화면에 접근해도 동일한 `next` 규칙을 적용한다.
- 오픈 리다이렉트 방지를 위해 `next`는 `/`로 시작하고 `//`로 시작하지 않는 내부 경로만 허용한다. 유효하지 않으면 `/`를 사용한다.
- `/?pick=1`로 돌아온 로그인 사용자는 `오늘 뭐 먹지?` 모달을 자동으로 한 번 열고, 가능하면 URL의 `pick` 값을 제거한다.
- 로그인·회원가입 화면에는 `맛집 목록 둘러보기` 링크를 추가해 비회원이 `/`로 돌아갈 수 있게 한다.

## 6. 등록·수정·삭제 보호

### 등록 `/register`

- 현재 등록 로직을 유지한다.
- 비회원 직접 접근 시 `/login?next=/register`로 이동한다.

### 수정 `/delivery/[id]/edit`

- 로그인만 확인해서는 안 된다.
- 데이터를 불러온 후 `item.user_id === user.id`인지 반드시 확인한다.
- 작성자가 아니면 폼을 렌더링하지 말고 상세 화면으로 돌려보내거나 `수정 권한이 없습니다`를 표시한다.
- 업데이트 쿼리에도 `.eq('user_id', user.id)`를 추가한다.
- 메뉴 교체 RPC는 기존 RLS 보호를 유지한다.

### 삭제

- 상세 화면의 버튼 숨김은 UX일 뿐 보안 수단이 아니다.
- 클라이언트 소유권 확인, 쿼리의 `user_id` 조건, Supabase RLS를 모두 유지한다.

## 7. Supabase RLS 및 권한

`deliveries`와 `delivery_menus` 양쪽 모두 공개 조회가 되어야 한다. 메뉴 테이블이 기존 `본인 메뉴 조회` 정책으로 남으면 비회원 상세와 목록에서 메뉴가 비어 보인다.

`supabase_setup.sql`에 멱등 방식으로 반영한다. 실제 대시보드의 기존 정책 이름도 확인해 중복 SELECT 정책을 정리한다.

```sql
-- deliveries: 공개 조회, 작성자만 쓰기
ALTER TABLE public.deliveries ENABLE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS "본인 데이터 조회" ON public.deliveries;
DROP POLICY IF EXISTS "맛집 공개 조회" ON public.deliveries;
CREATE POLICY "맛집 공개 조회"
ON public.deliveries FOR SELECT
USING (true);

DROP POLICY IF EXISTS "본인 데이터 생성" ON public.deliveries;
CREATE POLICY "본인 데이터 생성"
ON public.deliveries FOR INSERT
WITH CHECK (auth.uid() = user_id);

DROP POLICY IF EXISTS "본인 데이터 수정" ON public.deliveries;
CREATE POLICY "본인 데이터 수정"
ON public.deliveries FOR UPDATE
USING (auth.uid() = user_id)
WITH CHECK (auth.uid() = user_id);

DROP POLICY IF EXISTS "본인 데이터 삭제" ON public.deliveries;
CREATE POLICY "본인 데이터 삭제"
ON public.deliveries FOR DELETE
USING (auth.uid() = user_id);

GRANT SELECT ON public.deliveries TO anon, authenticated;
GRANT INSERT, UPDATE, DELETE ON public.deliveries TO authenticated;

-- delivery_menus: 공개 조회, 부모 맛집 작성자만 쓰기
DROP POLICY IF EXISTS "본인 메뉴 조회" ON public.delivery_menus;
DROP POLICY IF EXISTS "메뉴 공개 조회" ON public.delivery_menus;
CREATE POLICY "메뉴 공개 조회"
ON public.delivery_menus FOR SELECT
USING (true);

GRANT SELECT ON public.delivery_menus TO anon, authenticated;
GRANT INSERT, UPDATE, DELETE ON public.delivery_menus TO authenticated;
```

기존 `delivery_menus`의 INSERT/UPDATE/DELETE 정책과 `replace_delivery_menus` RPC 권한은 작성자 전용으로 유지한다. `auth.users`, 이메일, 인증 메타데이터를 공개 조회 대상으로 만들지 않는다.

## 8. 기존 기능에서 변경하지 말 것

- 수도권 시/도·시/군/구 목록 및 필터
- 음식 카테고리와 배달앱 필터
- 검색 및 정렬
- 최대 5개 메뉴와 대표 메뉴 1개 규칙
- 목록의 대표 메뉴 표시와 상세의 전체 메뉴 표시
- 오늘 뭐 먹지 추천 알고리즘과 화면
- 등록·수정 폼의 검증 규칙
- 기존 사용자 및 맛집 데이터

이번 작업에서 GPS, 지도, 배달 반경, 외부 배달앱 연동은 추가하지 않는다.

## 9. 필수 검증 시나리오

1. 로그아웃/시크릿 상태에서 `/` 목록이 보인다.
2. 비회원이 검색, 지역·카테고리·앱 필터, 정렬을 사용할 수 있다.
3. 비회원이 상세 페이지와 모든 등록 메뉴를 볼 수 있다.
4. 비회원 헤더에 로그인, 회원가입, 오늘 뭐 먹지, 맛집 등록이 보인다.
5. 비회원이 오늘 뭐 먹지/맛집 등록을 누르면 각각 올바른 로그인 안내 모달이 뜬다.
6. 모달의 로그인·회원가입을 거친 뒤 원래 요청한 기능으로 돌아간다.
7. 비회원이 `/register` 또는 편집 URL에 직접 접근하면 `next`를 보존한 로그인 화면으로 이동한다.
8. 로그인 회원은 기존 오늘 뭐 먹지와 맛집 등록 기능을 정상 사용한다.
9. 작성자 본인에게만 상세의 수정·삭제 버튼이 보인다.
10. 다른 회원이 편집 URL로 직접 접근해도 수정할 수 없다.
11. 다른 회원이 직접 UPDATE/DELETE 요청을 보내도 RLS가 거부한다.
12. 비회원의 SELECT는 성공하지만 INSERT/UPDATE/DELETE는 실패한다.
13. 로그아웃하면 로그인 화면이 아니라 공개 목록으로 돌아간다.
14. 데스크톱과 모바일에서 헤더가 겹치거나 가로로 넘치지 않는다.
15. `npm run build`가 성공하고 기존 등록·수정·메뉴 저장 기능에 회귀가 없다.

## 10. 완료 조건

- 위 권한표와 검증 시나리오를 모두 만족한다.
- 프런트엔드에서 버튼만 숨기는 데 그치지 않고 RLS까지 적용한다.
- SQL 변경은 `supabase_setup.sql`에 남기고 Supabase 대시보드에서 실행할 구간을 최종 보고한다.
- 변경 파일, 실행한 테스트, Supabase에서 사용자가 직접 실행해야 하는 작업을 작업 완료 메시지에 요약한다.
